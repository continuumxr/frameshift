## Cause of the run 1 / run 2 difference (same path, same pins): sample-PGO annotation depends on ASLR
- Of 4696 objects, 10 differ: 8 LLVM-bitcode TUs + their products (vmlinux.o, .btf.vmlinux.bin.o):
  fs/dcache.o fs/fs-writeback.o fs/proc/base.o kernel/cgroup/cgroup.o kernel/fork.o kernel/printk/printk.o
  kernel/sched/fair.o mm/kfence/core.o. (Run 2 vs run 3 gave a partly different set: fork, printk, sched/core,
  sched/fair, kfence/core.) llvm-dis of each: the only primary differences are profile metadata
  (function_entry_count, branch_weights, call-site !prof), e.g. dcache.o branch_weights 137 vs 136, proc/base.o
  function_entry_count 1495 vs 680; fork.o/fair.o/cgroup.o then make different inlining decisions (fork.o: 96 vs 95
  defined functions), and full LTO propagates the changed code into a shifted vmlinux layout.
- Isolated per-TU test (identical kbuild command line re-run 20x, tu_determinism.log):
    printk.o  ASLR on: 7 distinct outputs/20; setarch -R: 1/20; ASLR on + -fno-profile-sample-use: 1/20
    fair.o    ASLR on: 3 distinct/20;        setarch -R: 1/20; no profile: 1/20
    kfence/core.o ASLR on: 2 distinct/20;    setarch -R: 1/20; no profile: 1/20
  printk.o under setarch -R was also unchanged when the environment size was varied (1..4097 bytes; stack shift).
  So clang r450784e's -fprofile-sample-use annotation is address-dependent (iteration over a pointer-ordered
  structure); with ASLR off it is stable. Nothing in it is a timestamp or path. Modules happened to be stable
  (no module TU flipped in 4 runs) but are compiled with the same flag and are not guaranteed.
- The Quest 2 4.19 tree has no -fprofile-sample-use (Makefile grep 0), which is why its recipe sufficed.

## Original FS-A-006 build (out/) vs pinned builds: why it cannot be matched bit-for-bit
- .ko: all 272 differ only in debug info and the GNU build-id (object path ".../kgate27/out" vs ".../out-repro" in
  DW_AT_comp_dir; build-id hashes it). After llvm-objcopy --strip-debug --remove-section=.note.gnu.build-id: 272/272
  identical to run 1.
- vmlinux/Image: object path in debug info/build-ids (41 path strings in vmlinux), kheaders tar mtimes (unpinned
  original: wall-clock mtimes), initramfs cpio mtimes, AND the ASLR-dependent PGO annotation (e.g. fork.o
  release_task_stack entry count -1 vs 2; account_kernel_stack not inlined in run 1). The original was built
  with ASLR on and unpinned, so its exact code layout is not recoverable.
- Symbol-version interface is fully stable: Module.symvers (7b5cfa8f...) is identical in runs 1-4, and every run
  reproduces module_layout 0xb1f01218 and 2601/2601 vendor-required CRCs; the whole 14059-entry vmlinux CRC set
  equals ~/work/kgate27/built_vmlinux_crcs.txt. Sample-PGO changes code, not types, so CRCs never moved.

## Verdict
The Quest 3 v2.7 (5.10) tree is NOT bit-reproducible with the Quest 2 recipe (same path + pinned
KBUILD_BUILD_TIMESTAMP/USER/HOST/VERSION): vmlinux and Image differ run to run because Meta's stock config enables
CONFIG_META_SAMPLE_PGO and clang r450784e's sample-profile annotation varies with address-space randomisation.
It IS bit-reproducible (vmlinux, Image, Module.symvers, all 272 .ko) when, in addition, the whole build runs with
ASLR disabled (`setarch x86_64 -R make ...`), as runs 3 and 4 show. Not tested: whether ASLR-off output is also
independent of the object-directory path or of host/heap differences (keep the same path; pin the toolchain).
Future gate builds should use the same path, the four KBUILD_BUILD_* pins, and setarch -R. Alternatives not taken:
-fno-profile-sample-use / META_SAMPLE_PGO=n would be deterministic but changes code generation away from stock.
